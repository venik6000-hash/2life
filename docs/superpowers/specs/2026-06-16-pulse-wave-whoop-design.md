# «Моя волна» (Pulse-Wave) — design spec (WHOOP-first, гибрид)

Date: 2026-06-16
Status: approved direction, pending spec review → implementation plan
История: единая спека фичи. Консолидирует прежнюю «ручную» спеку «Волны» (удалена как
неактуальная) с переработкой под WHOOP. WHOOP — **основной** источник данных; ручной
чек-ин — fallback для клиентов без браслета.
Author: ideation (multi-agent debate) + брейншторм 2026-06-16 + верификация схемы БД 2life и
WHOOP API v2.

---

## 1. Проблема и цель

Клиентское приложение 2life — пассивный просмотрщик (анализы, мессенджер, назначения,
рекомендации). Клиенты заходят редко, «WOW» нет. Владелец хочет киллер-фичу, которая заставляет
клиента **возвращаться часто**, вызывает **восторг**, **делится без раскрытия медтайны** и
**реально полезна**.

Три жёстких ограничения владельца:
1. **Нет «биологического возраста»** (закрыто отдельно — «ВУП»).
2. **Движок вовлечения НЕ зависит от ритма забора крови.** Кровь берут только в **начале и конце**
   программы (месяцы между). Лаб-данные — фон, не пульс.
3. **Нет AI/LLM в медицине.** Никакой AI-интерпретации, советов, диагноза, прогноза. По возможности
   AI вообще нет.

Доп. находка: голый стрик приёма препаратов «недостаточно WOW».

## 2. Ключевая идея

Самый неиспользуемый разрыв — **месяцы между двумя заборами крови**, когда у клиента и врача нет
сигнала, и приложение «гаснет». Фича живёт в этом разрыве и строит **личную кривую самочувствия**.

Переработка под WHOOP: у клиентов есть браслеты WHOOP с непрерывной объективной физиологией.
WHOOP **отлично** закрывает объективную половину (сон, пульс покоя, ВСР, восстановление, нагрузка)
и **не закрывает вообще** субъективную (настроение, фокус, либидо). Поэтому:

- **WHOOP автоматически заполняет объективную половину кривой** — клиенту не нужно ничего вводить.
- **Остаётся 1 субъективный тап в день (настроение)** — то, что WHOOP не видит, и что было
  уникальным PRO-сигналом, которого у врача между заборами нет.
- **Кто без WHOOP** — пользуется обычным ручным чек-ином (полный набор 1–5).

Это даёт «проще клиенту и больше данных нам» одновременно, не убивая субъективный сигнал и
ежедневный ритуал.

## 3. Фича

Личная **кривая самочувствия (momentum curve)**, которая видимо растёт по ходу протокола. У WHOOP-
клиента объективная линия (восстановление) тянется сама, плюс ежедневный **1 тап настроения**
(😣😐🙂😀 → 1–5). Несправедливая, некопируемая часть: **реальный личный врач** видит тренд (внимание
рационируется детерминированным флагом) и **реагирует** — one-tap «отметил вашу неделю» на хорошей
неделе, человеческая заметка, пришпиленная к дню, где метрика повернула.

### WOW-моменты
- **Главный (≈нед. 3–4):** клиент отдаляет масштаб и видит, как его линия восстановления/сна
  пересекает базовую полосу вверх — с заметкой реального врача, пришпиленной к дню поворота.
  Абстрактный протокол становится лично пережитой, видимой победой.
- **Повторяющийся:** объективный спад (упало восстановление / вырос пульс покоя) — и врач пишет
  первым, в течение часов, без записи на приём.

### Почему закрывает все цели
- **Частый возврат:** WHOOP-данные обновляются ежедневно сами → утренний пуш «волна обновилась» →
  5-секундный тап настроения. Награда (кривая растёт, дельта «vs первая неделя») немедленная и
  отделена от редкого ответа врача, так что цикл переживает обычные дни.
- **WOW:** видеть собственную трансформацию, подписанную реальным врачом.
- **Полезно:** непрерывный объективный + субъективный сигнал, которого у врача между заборами нет;
  ранние объективные перегибы (см. §8.2) — реальная клиническая ценность.
- **Виральность (честная):** для дискретной обеспеченной когорты движок — это сам **опыт**
  (консьерж-престиж: «мой врач пишет мне про моё восстановление раньше ассистента»), без раскрытия
  медтайны, структурно некопируемо. Numberless «momentum ribbon» share-card и реферал («подари
  другу интейк») — приятные дополнения, **не** движок.

## 4. Решения (зафиксированы в брейншторме 2026-06-16)

| # | Вопрос | Решение |
|---|---|---|
| 1 | Роль WHOOP | **Гибрид**: WHOOP авто-заполняет объективную половину; ручной чек-ин — fallback. |
| 2 | Что клиент делает ежедневно | **1 тап настроения/день** (у WHOOP-клиента). Фокус/либидо ежедневно с него не собираем — осознанный размен ради «проще клиенту». |
| 3 | Как данные приходят | **Вебхуки WHOOP + ежедневная сверка-поллинг.** |
| 4 | Онбординг клиента | **2 кнопки**; вся техника — однократно на стороне владельца, клиенту невидима. |
| 5 | Где хранить метрики | **В wave-слое** (`wave_checkins`), не в новых таблицах и не в `analytics_*`. |
| 6 | Объём метрик | **Весь скоуп сразу** (recovery, ВСР, пульс, сон, нагрузка, вес). |

## 5. Опыт клиента и врача

### 5.1 Онбординг — ровно 2 кнопки
1. В разделе «Моя волна» — баннер «Подключи WHOOP — волна заполнится сама» → **«Подключить WHOOP»**.
2. Редирект на экран согласия **самого WHOOP** (клиент уже залогинен в приложении WHOOP) → **«Authorize»**.
3. Редирект обратно → «✓ WHOOP подключён». Дальше всё автоматически.

Клиент **не вводит** токены/ключи/настройки. Единственная не-2life поверхность — экран согласия
WHOOP. Всегда доступна кнопка **«Отключить WHOOP»**.

### 5.2 Ежедневный ритуал
- WHOOP-клиент: утренний пуш «🌊 Твоя волна обновилась» (после синка) → открыл → увидел кривую →
  **1 тап настроения** → сохранено в строку дня.
- Без WHOOP: базовый ручной чек-ин («отметь за 60 секунд», полный набор 1–5).
- Логика напоминаний **ветвится по наличию подключения** (§7.5).

### 5.3 Сторона врача
- В существующем client/Journal-вью — «Волна» (тренд) на каждого назначенного клиента + открытые
  `wave_flags`, которые **подсказывают** one-tap реакцию («система отметила перегиб — подтвердить/
  прокомментировать?»). Реакции идут через существующие messenger/ws/push примитивы.

## 6. Архитектура данных (и почему именно так)

### 6.1 Принципы (мировые практики)
1. **Форма хранения = паттерн доступа.** Частые датированные измерения → одна строка на наблюдение
   (не блоб на клиента). Это модель **FHIR `Observation`**; существующий `analytics_values` — её
   лёгкая версия; данные WHOOP — просто ещё «Observation».
2. **Натуральный ключ + upsert для идемпотентности.** `UNIQUE(client_id, checkin_date)` глушит
   повторные вебхуки/ретраи (как `UNIQUE(marker_id, date)` у анализов).
3. **Секреты — отдельно от данных.** OAuth-токены (ротация/отзыв/шифрование) **никогда** не лежат
   в медзаписи → своя таблица.
4. **Провенанс.** `source` + `ingested_at`: будущие устройства добавляются, каждое число аудируемо.
5. **Хранить сырое, выводить на чтении.** momentum/перегибы считаем при чтении — никаких вердиктов
   в хранилище (держит «не диагноз / no AI»).
6. **PII-жизненный цикл.** Шифрование at-rest + согласие + удаление при отключении (152-ФЗ/GDPR).

Контекст существующей схемы: 2life уже использует разные формы под разные данные — `clients` (тонкая
строка), `stages.*_json` (документ-блоб для редко меняющегося конфига: анкета/питание/диагнозы),
`analytics_values` (нормализованный time-series анализов), `*_revisions` (версионированные документы).
WHOOP — это ежедневный time-series → ложится в нормализованную сторону, в wave-слой.

### 6.2 Модель данных

**Существующие wave-таблицы (создаются этой же фичей), additive через `runOnce`-миграции
(`server/services/migrations.js:18`); `clients.id` — TEXT:**

- `wave_checkins` — одна строка на (клиент × день), upsert:
  ```
  id, client_id (TEXT FK clients.id), user_id (INT FK users.id), checkin_date DATE,
  scores JSONB,            -- субъективное: у WHOOP-клиента {mood:1..5}; у ручного — полный набор
  context_tags JSONB, note TEXT,
  objective JSONB DEFAULT '{}',          -- объективный блок WHOOP за день  (см. 6.3)
  source TEXT DEFAULT 'manual',          -- происхождение objective: 'whoop'|'manual'
  ingested_at TIMESTAMPTZ,               -- когда подтянули WHOOP (vs created_at)
  weight NUMERIC NULL, resting_hr INT NULL,
  created_at, updated_at,
  UNIQUE(client_id, checkin_date)
  ```
- `wave_reactions` — пины/ack врача: `id, client_id, author_user_id, pinned_date DATE,
  kind ('ack'|'note'), text, created_at`.
- `wave_flags` — детерминированные сигналы внимания (без AI): `id, client_id, flag_date DATE,
  kind ('inflection_down'|'inflection_up'|'severe_low'), metric TEXT, magnitude, status
  ('open'|'addressed'|'dismissed'), created_at`, `UNIQUE(client_id, flag_date, kind)`.

**Новая таблица — `integration_connections`** (обобщённая по источнику; вся WHOOP-дельта поверх
wave-таблиц = эта 1 таблица + 3 колонки в `wave_checkins`):
```
id, client_id (TEXT FK), user_id (INT FK),
source            TEXT NOT NULL                 -- 'whoop' (позже 'oura'|'apple')
provider_user_id  TEXT                          -- whoop_user_id, для поиска по вебхуку
access_token_enc  TEXT NOT NULL                 -- шифрованный
refresh_token_enc TEXT NOT NULL                 -- шифрованный
token_expires_at  TIMESTAMPTZ
scopes            JSONB DEFAULT '[]'
status            TEXT DEFAULT 'active'          -- active|revoked|error
connected_at, last_sync_at, last_error
UNIQUE(client_id, source)
```

### 6.3 Полный набор метрик WHOOP (весь скоуп в MVP)

| Метрика | Источник (v2) | Поле в `objective` | Роль |
|---|---|---|---|
| Восстановление, % | recovery | `recovery` | **главная линия** (hero), флаг (↓) |
| Пульс покоя, уд/мин | recovery | `rhr_bpm` | линия + флаг (**↑ = тревога**) |
| ВСР (rmssd), мс | recovery | `hrv_ms` | линия + флаг (↓) |
| Сон, % | activity/sleep | `sleep_perf` | линия + флаг (↓) |
| Частота дыхания | activity/sleep | `respiratory_rate` | линия (контекст) |
| Нагрузка (strain) | cycle | `strain` | **линия-контекст, НЕ источник флагов** |
| Вес, кг | body measurement | `weight` | линия (**может быть разреженной** — WHOOP вес сам не меряет) |

## 7. Интеграция WHOOP (механика)

**API:** WHOOP Developer API **v2** (v1 отключён после 2025-10-01 — строим только v2), OAuth 2.0.
Скоупы: `read:recovery`, `read:sleep`, `read:cycles`, `read:workout`, `read:body_measurement`,
`read:profile`, `offline`. Эндпоинты: `GET /v2/recovery`, `GET /v2/activity/sleep`, `GET /v2/cycle`,
body-measurement (точный путь v2 — подтвердить по docs). Вебхуки v2 — на UUID; recovery-событие
ссылается на UUID сна.

### 7.1 OAuth-подключение
- `GET /api/wave/whoop/connect` — формирует authorize-URL (client_id, redirect_uri, scopes, `state`
  с CSRF-защитой), редиректит клиента.
- `GET /api/wave/whoop/callback` — принимает `code`, проверяет `state`, меняет на токены, шифрует и
  кладёт в `integration_connections`, подтверждает подписку вебхуков, делает первичный **backfill**
  (последние ~30–90 дней recovery/sleep/cycle).

### 7.2 Вебхуки + сверка
- `POST /api/wave/whoop/webhook` — **проверяет подпись WHOOP**, по `provider_user_id` находит
  подключение, тянет обновлённые recovery/sleep/cycle, маппит в `objective`, upsert в `wave_checkins`
  за дату, гоняет скан перегибов, шлёт пуш «волна обновилась» + ws клиенту.
- **Сверка**: в существующем блоке 9:00 планировщика (`startJournalNotificationScheduler` —
  `server/services/journalNotifications.js:48`) — для каждого `active`-подключения с устаревшим
  `last_sync_at` тянем последнее. Ловит непришедшие вебхуки.

### 7.3 Новые серверные модули
- `server/services/whoopClient.js` — OAuth (authorize-URL, обмен кода, refresh-on-401) + фетчеры
  `/v2/...`. Тонкая HTTP-обёртка, без БД.
- `server/services/whoopStore.js` — CRUD подключений (шифрование токенов), маппинг, оркестрация
  синка, backfill.
- `server/routes/whoopWebhook.js` (или внутри `routes/wave.js`) — connect/callback/webhook.

### 7.4 Маппинг payload → `objective`
`mapWhoopToObjective({recovery, sleep, cycle, body})` → нормализованный `objective` с округлениями,
без отсутствующих полей. Чистая функция, тестируется отдельно, **без AI**.

### 7.5 Напоминания (ветвление в client-lane)
Зеркалим существующий журнальный планировщик, но новый client-lane (журнальный жёстко на
`is_client=false`; наш — на `is_client=true`, секция `wave`):
- WHOOP-клиент: «волна обновилась» по факту синка (вебхук); если за утро синка не было — обычный нудж.
- Без WHOOP: дневной чек-ин-нудж.
- Идемпотентность — через существующий `journal_notification_deliveries`
  (`wasJournalNotificationDelivered`/`recordJournalNotificationDelivery`,
  `server/services/journalStore.js:176-191`), distinct `kind` (`wave_whoop_update`/`wave_checkin`).

## 8. Кривая и флаги

### 8.1 Кривая (честно к «не диагноз / no AI»)
- Нет charting-либы в репо → **hand-rolled SVG** (как задумано). Переиспользуем `ScoreBar`
  (`src/components/ScoreBar.jsx`) и таксономию `WELLBEING_SPEC` для ручного чек-ина.
- **Главная линия = `recovery %`** WHOOP, как тренд к личной базовой полосе. Никогда — красно-зелёный
  вердикт WHOOP; никогда — выдуманный composite-«балл здоровья».
- Переключаемые линии: пульс покоя, ВСР, сон, нагрузка(контекст), вес.
- **Настроение** из тапа — цветными точками на главной линии + плашка «vs первая неделя».
- Без WHOOP — базовая субъективная кривая. Компонент ветвится по «есть подключение?».
- Дисклеймер: «это твои тренды, не диагноз; срочное — в мессенджер или звонок врачу».

### 8.2 Детерминированные флаги (per-metric, без AI)
- `detectInflection` (pure, `server/services/waveMath.js`) обобщается на несколько рядов; каждый флаг
  тегируется `metric` (колонка уже в `wave_flags`).
- Направление: `recovery ↓`, `сон ↓`, `ВСР ↓`, **`пульс покоя ↑`** → флаг-тревога; `recovery ↑` →
  позитивный перегиб. **`strain` — не источник флагов.**
- Субъективный severe-low floor (настроение) и любая свободная заметка — всегда доходят до человека,
  минуя пороги.

## 9. API

Клиент-scoped (пишет/читает только свою запись — см. §10):
- `POST /api/clients/:id/wave/checkin` — upsert настроения/ручного чек-ина за сегодня.
- `GET  /api/clients/:id/wave/series?from&to` — данные кривой (клиент: свои; врач: назначенные).
- `GET  /api/clients/:id/wave/today` — состояние сегодня для ритуала.

Доктор-scoped (только назначенные клиенты):
- `GET  /api/wave/flags` — открытые перегибы по доступным клиентам.
- `POST /api/clients/:id/wave/reaction` — ack/note к дню; push+ws клиенту; флаг → `addressed`.

WHOOP:
- `GET  /api/wave/whoop/connect`, `GET /api/wave/whoop/callback`, `POST /api/wave/whoop/webhook`.
- `POST /api/wave/whoop/disconnect` — отзыв токена + остановка синка + опц. hard-purge.

## 10. Безопасность и приватность
- **Клиент → только своя запись.** `canAccessClient` (`server/services/clientAccess.js:3`) —
  staff-facing; добавить client-owns-record проверку (выводит разрешённый `client_id` из
  аутентифицированного client-user через `client_assignments`), отвергать несовпадение. Свой
  verify-скрипт.
- **Врач → только назначенные** (`canAccessClient` / `all_clients_access`).
- **Секция** `wave` в `role_sections` (gated `is_client` + право секции); напоминание уважает право
  секции точно как журнал.
- **Токены WHOOP** — только в `integration_connections`, **шифрованные at-rest** (механизм
  мессенджера), никогда не уходят на клиент.
- WHOOP-данные — чувствительный непрерывный PII → наследуют шифрование + section-права + scoping.
- **Экран согласия (наш, до редиректа в WHOOP)** прямым текстом: что тянем, что видит врач, что
  отключается в любой момент.
- **Отключение**: отзываем токен у WHOOP, `status='revoked'`, синк стоп; предлагаем **удалить
  собранные данные WHOOP** (hard-purge `objective`-блоков + подключения) — 152-ФЗ/GDPR.
- Push-пейлоады content-free; severe-low floor и свободная заметка всегда доходят до человека;
  реакции врача celebratory/non-diagnostic. Share-card numberless.

## 11. Проверки (как принято: `verify*.mjs` / `smoke*.js`)
- `verify:wave-checkin-perms` — клиент трогает только свою запись; staff/client-гейты держат.
- `verify:wave-reminder-lane` — client-lane срабатывает, уважает право секции + идемпотентность;
  не пересекается со staff-lane.
- `verify:wave-inflection` — детерминированная математика флагов, **per-metric** (recovery↓, rhr↑,
  hrv↓, sleep↓; strain не флагуется; severe-low floor).
- `verify:wave-reaction-delivery` — реакция → push + ws + пин.
- `verify:wave-static` — секция зарегистрирована, дисклеймеры на месте, кнопки connect/disconnect,
  роуты под гвардами.
- `verify:whoop-mapping` — payload → `objective` (чистая, без БД/сети).
- `verify:whoop-oauth` — authorize-URL + логика refresh (мокабельно).
- `smoke:whoop-store` — CRUD подключения + round-trip шифрования + upsert `objective`.
- `verify:whoop-webhook-perms` — проверка подписи вебхука + поиск подключения; клиент видит только своё.

## 12. Объём: MVP vs позже
- **MVP (всё WHOOP сразу + база «Волны»):** wave-таблицы + ритуал-UI + своя кривая + client reminder-
  lane + доктор flag→one-tap reaction; **+** OAuth connect/disconnect + хранение токенов + вебхук-приём
  (recovery+sleep+cycle) + сверка + backfill + полный `objective`-набор (вкл. ВСР/пульс/нагрузку/вес) +

## 13. Операционные предусловия (однократно, на стороне владельца)
- Зарегистрировать приложение в кабинете разработчика WHOOP: `client_id`/`secret`,
  `redirect_uri = https://<хост>/api/wave/whoop/callback`, подписка на вебхуки.
- Секреты — в env, не в коде.
- **Подтвердить лимит пользователей** dev-приложения WHOOP (исторически есть кап до ревью; на ~7
  клиентов скорее всего хватает дефолта).
- У клиента — **активная подписка WHOOP**, иначе данные не отдаются.

## 14. Открытые вопросы для планирования
1. **Active client count** — дебаты оценили ~7; подтвердить dev-seed vs prod (влияет на cohort-фазы
   и лимит WHOOP-приложения).
2. **`client_id`↔`user_id` linkage** — один client-user = один `client_id` (load-bearing для scoping
   и записи, и WHOOP-подключения). Сверить `client_assignments`/`is_client`.
3. **Точные пути/поля v2** (особенно body-measurement и имена полей recovery/sleep) — сверить по
   актуальным docs WHOOP перед кодом.
4. **Проверка подписи вебхука** — формат заголовка/HMAC WHOOP v2 (уточнить из docs).
5. **Окно backfill** при подключении — 30 или 90 дней (красивая кривая сразу vs объём).
6. **Шкала субъективного** — настроение 1–5 (рекомендуется быстрый 1–5 вместо 1–10).
